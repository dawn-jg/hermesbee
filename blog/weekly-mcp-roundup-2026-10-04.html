Weekly MCP Roundup: Agent Skills Join the Spec, the Stateless Era Begins and OpenAI Opens the ChatGPT Plugin SDK (Oct 4, 2026)

By HermesBee Team · Developer Tools · October 4, 2026 · 6 min read

Two protocol-level events and one vendor opening define this week in MCP. The Agent Skills extension (SEP-2640) merged as Final, making skill:// resources and a skills/list / skills/get interface part of the standard. On 2026-09-28 the Agentic AI Foundation formally ratified the stateless architecture the July 2026 spec previewed. And OpenAI published its official ChatGPT MCP plugin SDK. The supply side kept compounding in parallel: 19,831+ public servers and roughly 97 million monthly SDK downloads.

Agent Skills become a protocol extension

SEP-2640, the "Skills Extension", merged as Final on 2026-09-13 — the first SEP ratified after the 2026-07-28 release. It specifies how an MCP server exposes Agent Skills as first-class resources:

  • a skill:// URI convention for addressing one skill;
  • two required methods, skills/list and skills/get, for discovery and retrieval;
  • an optional resources/directory/read for directory-style access;
  • the extension identifier io.modelcontextprotocol.skills.

Until now, "skills" were a per-harness private feature: a folder one client loaded and another ignored. SEP-2640 turns the concept into a portable format with standard discovery and retrieval, and MCP Inspector supported it four days early in 2.6.0. The practical consequence for anyone maintaining a local skill library is that the shape you already use becomes addressable by any compliant server — and the missing piece in the market is now a distribution layer rather than a format.

The stateless spec is ratified

On 2026-09-28 the Agentic AI Foundation — a directed fund under the Linux Foundation — shipped the largest MCP update to date. The stateless architecture is final: no handshake, no Mcp-Session-Id, no sticky routing. OAuth issuer (iss) validation is mandatory, a formal 12-month deprecation policy now applies to protocol features, and MCP Apps and MCP Tasks graduated from extension drafts to official extensions. The official Go SDK v1.8.0 hardened resource-exhaustion limits across JSON nesting depth, SSE event size, stdio frame length and OAuth DCR responses.

Any MCP product written against session assumptions needs its transport layer rewritten against the "modern (2026-07-28+)" model. The upside is concrete: stateless servers run directly on Cloudflare Workers, which cuts hosting cost and removes the sticky-session routing problem that made third-party MCP hosting awkward.

OpenAI opens the ChatGPT plugin SDK

openai/mcp-extensions (Apache-2.0) is the official way to give an MCP server native-feeling capabilities inside ChatGPT:

  • sidebar entrypoints — your tool gets its own panel;
  • custom viewers for specific file types;
  • @-mentions in the composer;
  • rich forms (image picker, form elicitation) so the agent can request structured input.

npm @openai/mcp-extensions is published at v0.1.0 (a PyPI package exists too), the repo passed ~719★ this week, and it is under active push. It is early — a 0.1.0 API will move, and the plugin review bar is not public. The sensible move is to wrap one existing server as a demo shell before planning reuse; the value is a second distribution surface alongside the existing MCP directories.

The economics are still the hard part

The MCP protocol has no billing layer — the official documentation says so — which is why four monetization models run in parallel with no clear winner.

Field reports from 2026 put the realistic ceiling at $500–$10,000+ per month, with most public success stories landing between $500 and $3,000. Three rules recur in every honest write-up: don't hand out free quota measured in "number of calls" (tie it to real cost, because an agent burns a human month in seconds); separate the buy decision (a human, monthly) from the spend decision (an agent, credits); and price the most expensive tool separately, or agents will target it first.

Security and governance

The MCP Security Working Group published threat model v1.0 — prompt injection via tool output, supply-chain risk, privilege escalation — now cited as a non-normative appendix to the spec. RFC-0041 proposes a standard error envelope for tool calls (code / message / retryable). On the client side, Claude Desktop 0.9.4 made per-server tool confirmation standard: always confirm, confirm writes only, or never. If you skipped last week's MCP server security guide, the short version is unchanged — pin versions, scope filesystem access, and never trust a tool description.

Supply gaps worth claiming

  • Skills distribution — SEP-2640 defines the interface, but nobody has shipped the "npm for skills" it implies.
  • App-store operations MCP — magaza-mcp covers App Store Connect and Google Play in ~87★ and Turkish only.
  • Local-first agent observability — agent-console (~795★) records tokens, cache and cost per session, but is built for the developer who wrote it, not for buyers.
  • AI documentation lint — seiso (~173★, Rust, published to crates.io / npm / PyPI) proves real demand for checking AI-written Markdown against conventions.

How we evaluate MCP servers

Unchanged, and this week reinforced it: does it handle the messy 30% — anti-bot walls and dynamic pages (see our Cloudflare guide)? Does it run locally and bill once rather than meter every call? Does it return structure instead of raw HTML, since raw HTML is a context tax paid on every call (see the MCP scraping guide)? And does it pass a security review before touching your data? HermesBee's take

Two of this week's three headlines push the same way as our line. Statelessness favours lean, self-hosted servers over hosted middleware, and the Skills extension makes a local skill library portable instead of client-locked. That is why we keep shipping Unified Scraper MCP, CF Bypass Browser MCP, LLM Scraper MCP and the rest of the catalog as local, buy-once, auditable tools — no account, no cloud dependency, no per-call meter. When the spec itself starts standardizing discovery and delivery, the architecture we chose stops being a preference and starts being the default shape.
